# ClearClose — ระบบกระทบยอดบัญชี

กระทบยอด **รายการรับเงิน ↔ รายการเดินบัญชีธนาคาร** จากเอกสารจริงในโฟลเดอร์ `data/`
ระบบไม่มีข้อมูลตัวอย่างหรือข้อมูลที่พิมพ์ไว้ล่วงหน้าเลย ทุกตัวเลขที่แสดงบนหน้าจอถูกอ่านมาจากไฟล์ต้นฉบับ

## กฎการจับคู่ (ruleset v3.0.0)

**การจับคู่อัตโนมัติ** จะสำเร็จก็ต่อเมื่อ **เงื่อนไขทั้งสองข้อเป็นจริงพร้อมกัน**

| | กฎ | รายละเอียด |
|---|---|---|
| R01 | วันที่สร้างคำจอง = วันที่เงินเข้า Statement | ใช้ `Reservation Creation Time` จากบัญชีแยกประเภท เทียบเป็น**วันปฏิทินเดียวกัน** ไม่มี date window |
| R02 | ยอดต้องตรงกันพอดี | ผลต่างต้องเป็น `฿0.00` ไม่มี tolerance |

เมื่อทั้งสองข้อผ่าน ระบบจะจับคู่ตามลำดับ

| | รูปแบบ | score |
|---|---|---|
| R00 | คู่ที่**ผู้ตรวจกดยืนยันเอง** ถูกล็อกก่อนกฎอัตโนมัติทุกข้อ | 100 |
| R03 | `1:1` หนึ่งรายการรับเงิน = หนึ่งยอดเงินเข้า | 100 |
| R04 | `N:1` ผลรวมหลายรายการรับเงินในวันเดียวกัน = หนึ่งยอดเงินเข้า | 95 |
| R05 | `1:N` หนึ่งรายการรับเงิน = ผลรวมหลายยอดเงินเข้าในวันเดียวกัน | 92 |
| R06 | ที่เหลือทั้งหมดเป็นข้อยกเว้น | — |

ระบบ **ไม่ปรับยอด ไม่ขยายช่วงวันที่ และไม่แก้ไขข้อมูลต้นฉบับ** ให้อัตโนมัติ
สิ่งเดียวที่ยอมรับคู่นอกกฎได้คือ **คน** — ดูหัวข้อ [การจับคู่เอง](#การจับคู่เอง-r00)
รายการที่จับคู่ไม่ได้จะถูกจัดเข้าคิวตรวจสอบพร้อมเหตุผล:

- `MISSING_BOOKING` — เลขที่จองไม่มีในบัญชีแยกประเภท จึงไม่มีวันที่สร้างคำจองให้เทียบ
- `DATE_RULE_UNMET` — ไม่มีเงินเข้าบัญชีนั้นเลยในวันที่สร้างคำจอง (ไม่ผ่าน R01)
- `AMOUNT_MISMATCH` — มีเงินเข้าวันเดียวกัน แต่ไม่มียอดหรือชุดยอดใดรวมแล้วเท่ากันพอดี (ไม่ผ่าน R02)
- `UNMATCHED_BANK_CREDIT` — เงินเข้าที่ยังไม่มีรายการรับเงินผ่านกฎทั้งสองข้อมารองรับ
- `REFUND_LINE` — รายการคืนเงิน ต้องกระทบกับยอดถอน ไม่ใช่ยอดฝาก

ช่องทางรับเงินที่ไม่มี Statement ในโฟลเดอร์ `data/` (เช่น `Kbank-Posh`, เงินสด)
จะถูกรายงานแยกเป็น **นอกขอบเขต** ไม่นับเป็นทั้งจับคู่สำเร็จและข้อยกเว้น

## การจับคู่เอง (R00)

กฎ R01/R02 เข้มโดยตั้งใจ ผลคือรายการจำนวนหนึ่งจับคู่อัตโนมัติไม่ได้ทั้งที่มันคือเงินก้อนเดียวกันจริง ๆ
หน้า **ยอดที่ไม่ตรง** จึงเปิดให้ผู้ตรวจหยิบรายการรับเงินฝั่งหนึ่ง หยิบเงินเข้าธนาคารอีกฝั่งหนึ่ง
แล้วกดยืนยันว่าสองกองนี้คือเงินก้อนเดียวกัน ระบบเรียงตัวเลือกให้ตาม **ยอดที่ยังขาด** แล้วจึงตามวันที่ใกล้ที่สุด

ถ้ายอดสองฝั่งไม่เท่ากัน **ยืนยันได้ แต่ต้องเลือกเหตุผล** ก่อนเสมอ

| เหตุผล | ใช้เมื่อ |
|---|---|
| `COMMISSION` | OTA หักค่าคอมก่อนโอน |
| `BANK_FEE` | ค่าโอน ค่าธรรมเนียมต่างประเทศ |
| `ROUNDING` | ต่างกันไม่กี่สตางค์ |
| `DISCOUNT` | รับจริงน้อยกว่ายอดที่บันทึกไว้ |
| `EXTRA_CHARGE` | รับจริงมากกว่ายอดที่บันทึกไว้ |
| `OTHER` | ต้องเขียนหมายเหตุกำกับ |

ผลต่างที่ยอมรับ **ไม่ถูกกลบให้เป็นศูนย์** — มันถูกบันทึกไว้บนกลุ่มนั้น รวมยอดไว้ในรายงานว่า
"ผลต่างที่รับไว้" และติดไปกับไฟล์ CSV ด้วย กด **ยกเลิก** เมื่อไหร่ รายการก็กลับเข้าคิวงานเหมือนเดิม

การตัดสินใจถูกเก็บแยกจากเอกสาร (`clearclose.match_decisions`) **อัปโหลดเอกสารทับของเดิมไม่ทำให้หาย**
ถ้าแถวที่อ้างถึงไม่มีอยู่จริงแล้ว ระบบจะรายงานว่าการจับคู่นั้นใช้ไม่ได้ ไม่ใช่เงียบหาย

## การแตกยอดก้อนโอน OTA

Airbnb, Trip.com และ Booking.com ไม่ได้โอนทีละคำจอง แต่รวบหลายคำจองมาเป็นก้อนเดียว
**หลังหักค่าคอมแล้ว** ยอดที่เข้าบัญชีจึงไม่มีทางเท่ากับยอดที่บันทึกไว้ กฎ R02 จับไม่ได้ตามธรรมชาติ

หน้า **ก้อนโอน OTA** ทำงานแบบนี้

1. หาเงินเข้าที่ยังไม่มีใครจับ และข้อความบนบรรทัดเข้าข่ายเป็นก้อนโอน OTA
   (ค่าตั้งต้น: `ธุรกรรมต่างประเทศ`, `SMART SCBT`, `NRBA`, `MCP Operating`)
2. ดูรายการรับเงินช่องทาง OTA ที่วันอยู่ในช่วง **±7 วัน** รอบก้อนนั้น
3. เสนอชุดที่ยอดเต็ม **ท่วมก้อนโอนน้อยที่สุด** — ยอดเต็มต้อง ≥ เงินที่เข้าเสมอ เพราะคอมถูกหักไปแล้ว
   ส่วนที่เกินคือค่าคอม พร้อมบอกเป็นเปอร์เซ็นต์
4. ผู้ตรวจติ๊กเพิ่ม/ออกได้ แล้วกดยืนยัน — ก่อนกด **ตัวเลขทุกหน้าไม่ขยับเลย**

คอมเกินเพดานที่ตั้งไว้ (ค่าตั้งต้น 30%) จะขึ้นธง "ต้องดูก่อน" ไม่ได้ถูกห้าม
รายการรับเงินหนึ่งใบถูกเสนอให้ก้อนเดียวเท่านั้น

> ข้อเสนอเป็น **การเดาที่มีหลักการ** ไม่ใช่คำตอบ ชุดที่ยอดลงตัวพอดีอาจเป็นเรื่องบังเอิญได้
> หน้าจอจึงแสดงทุกคำจองในก้อนพร้อมวันที่ห่างจากก้อนโอนกี่วัน ให้ตัดสินก่อนกดยืนยันเสมอ

## ฐานข้อมูลและการนำเข้าเอกสาร

ระบบอ่านข้อมูลได้สองทาง และเลือกให้อัตโนมัติ

| เงื่อนไข | แหล่งข้อมูล |
|---|---|
| ตั้ง `DATABASE_URL` | reconciliation run ล่าสุดใน **Neon Postgres** — คือสิ่งที่การอัปโหลดผ่านเว็บเขียนลงไป |
| ไม่ได้ตั้ง | ชุดข้อมูลที่ build จาก `data/` ตอน build time |

ตั้งค่าให้ใช้ฐานข้อมูล:

1. คัดลอก connection string จาก Neon — **ใช้ project/database ที่มีอยู่แล้วได้** ไม่ต้องสร้างใหม่
2. Vercel → Settings → Environment Variables → เพิ่ม `DATABASE_URL`
3. Redeploy — ระบบสร้าง schema และตารางเองอัตโนมัติในการเรียกครั้งแรก (`migrate()` เป็น idempotent)

ออบเจ็กต์ทั้งหมดอยู่ใน schema ชื่อ **`clearclose`** ไม่ใช่ `public` ระบบจึงใช้ database
ร่วมกับแอปอื่นได้โดยไม่ชนกัน แม้แอปนั้นจะมีตารางชื่อ `documents` หรือ `receipts` อยู่แล้ว
(มีเทสต์คุมกรณีนี้ไว้) ถ้าต้องการลบระบบออกทั้งหมดคือ `DROP SCHEMA clearclose CASCADE;`

จากนั้นอัปโหลดเอกสารได้ที่หน้า **นำเข้าเอกสาร** เลือกได้ทีเดียวทั้งสี่ไฟล์
ระบบดูจากชื่อไฟล์ว่าเป็นเอกสารชนิดใด แล้ว parse → เก็บลง Postgres → กระทบยอดใหม่ทั้งระบบ

ตาราง: `documents`, `document_files`, `bookings`, `receipts`, `bank_statements`,
`bank_transactions`, `reconciliation_runs`, `match_decisions`, `app_settings`,
`audit_events`, `schema_migrations`
— เงินเป็น integer สตางค์เสมอ ไม่ใช้ float
และวันที่ทางบัญชีเก็บเป็น `text` รูป ISO เพื่อไม่ให้ timezone เลื่อนวัน

การเปลี่ยนโครงสร้างตารางเดินผ่าน migration ที่รันครั้งเดียวและบันทึกไว้ใน
`schema_migrations` ฐานข้อมูลที่มีข้อมูลอยู่แล้วถูกอัปเกรดในที่ ไม่ต้องอัปโหลดเดือนเก่าซ้ำ

### งวดบัญชี — เก็บได้หลายเดือน

ทุกแถวถือ**งวดของวันที่ตัวเอง** (`YYYY-MM`) ไม่ใช่งวดของไฟล์ที่มันมา ระบบจึงไม่ต้องถามว่า
ไฟล์นี้เป็นของเดือนไหน และไฟล์ที่คร่อมเดือนก็ลงตารางถูกต้อง

| อัปโหลด | ผลกับข้อมูลเดิม |
|---|---|
| ไฟล์ของเดือนใหม่ | เพิ่มเข้าไป **เดือนเก่าไม่ถูกแตะ** |
| ไฟล์ชนิดเดิมของเดือนเดิม | แทนที่**เฉพาะเดือนนั้น** เดือนอื่นไม่ถูกแตะ |
| statement ของบัญชีเดิมคนละเดือน | เก็บเพิ่ม — หนึ่งบัญชีมี statement ได้เดือนละฉบับ |

หน้าจอมีตัวเลือก **งวด** ที่แถบบน เลือกดูทีละเดือนหรือทุกงวดรวมกันได้
การกระทบยอดคำนวณครบทุกงวดพร้อมกันเสมอ ตัวเลือกงวดกรองเฉพาะ*สิ่งที่แสดง* —
ต้องเป็นแบบนี้ ไม่งั้นเงินที่ข้ามเดือนจะหาคู่ไม่เจอ

ไฟล์ต้นฉบับ (PDF/XLSX) ถูกเก็บไว้ใน `document_files` ด้วย กดดาวน์โหลดย้อนหลังได้รายงวด
ที่ท้ายหน้า **นำเข้าเอกสาร** (ไฟล์เกิน 8 MB จะไม่ถูกเก็บสำเนา แต่ข้อมูลยังเข้าครบ)

### เงินที่เหลื่อมเดือน

OTA รับเงินจากลูกค้าเดือนหนึ่ง แล้วรอบโอนตกไปอีกเดือนหนึ่งหลังหักค่าคอม
กฎอัตโนมัติ **R01 (วันเดียวกันเป๊ะ) ไม่ถูกผ่อนให้เลย** — เงินข้ามเดือนเดินผ่านทางเดียวคือ
**ก้อนโอน OTA**: ระบบเสนอว่าก้อนนี้น่าจะเป็นของคำจองไหนบ้างภายในช่วงวันที่ตั้งไว้
แล้วคนกดยืนยันพร้อมเหตุผล ค่าคอมถูกรายงานเป็นผลต่างที่ยอมรับ ไม่ถูกกลบ

กลุ่มที่เหลื่อมเดือนติดป้าย **↷** และ**เห็นได้จากทั้งสองงวด** เปิดกรกฎาคมก็รู้ว่ารายการใบนี้
เคลียร์ไปแล้วด้วยเงินที่เข้าเดือนสิงหาคม ส่วนการนับยอด: จำนวนรายการนับในเดือนที่บันทึกรับเงิน
ยอดเงินนับในเดือนที่เงินเข้าบัญชีจริง เงินก้อนเดียวกันจึงไม่ถูกนับสองเดือน

ถ้าอัปโหลดรายงานการรับเงินของเดือนใหม่มาก่อน statement ระบบจะรายงานว่า
**"ยังไม่มี Statement ของงวดนี้"** ตรง ๆ แทนที่จะโยนรายการทั้งเดือนเป็นข้อยกเว้นลวง

## ข้อมูลต้นทาง

วางไฟล์ทั้งสี่ไว้ใน `data/` แล้วรัน `npm run data:build`

| ไฟล์ | เนื้อหา |
|---|---|
| `บันทึกบัญชีแยกประเภท*.xlsx` | Ledger — เลขที่จอง, **วันที่สร้างคำจอง**, ยอดจอง, ช่องทางชำระ |
| `รายงานการรับเงิน*.xlsx` | Collection report — วันที่, ช่องทาง, ยอด, เลขที่จอง |
| `885*.pdf` | Statement KBank ของช่องทาง `KbankGL885` |
| `987*.pdf` | Statement KBank ของช่องทาง `KbankGL987` |

เลขที่บัญชี ชื่อลูกค้า และยอดเงินทั้งหมดถูกอ่านจากไฟล์ตอน build ไม่มีค่าใดถูกเขียนลงในซอร์สโค้ด

**`data/` ไม่ถูก commit ขึ้น git โดยตั้งใจ** เพราะเป็นข้อมูลการเงินและข้อมูลส่วนบุคคลจริง
`data:build` จึงรองรับสามสถานะ:

| สถานะของ `data/` | ผล |
|---|---|
| ว่าง / ไม่มีโฟลเดอร์ | สร้างชุดข้อมูลเปล่า build ผ่าน ระบบขึ้นหน้า "ยังไม่มีเอกสารต้นทาง" |
| ครบทั้งสี่ไฟล์ | กระทบยอดเต็มรูปแบบ |
| มีบางไฟล์ | **build หยุดพร้อมบอกว่าขาดไฟล์ใด** — กันไม่ให้ได้ตัวเลขที่กระทบยอดไม่ครบ |

สคริปต์อ่านไฟล์เอง ไม่ต้องแปลงเป็น CSV ก่อน:

- `scripts/lib/zip.mjs` + `scripts/lib/xlsx.mjs` — อ่าน `.xlsx` โดยตรง
- `scripts/lib/pdf.mjs` + `scripts/lib/statement.mjs` — ถอดข้อความพร้อมตำแหน่งจาก Statement PDF
  แล้วประกอบเป็นรายการเดินบัญชี พร้อมตรวจ control total (`ยอดยกมา + ฝาก − ถอน = ยอดยกไป`)

ผลลัพธ์คือ `lib/dataset.generated.json` ซึ่ง UI และ `/api/dataset` ใช้ร่วมกัน

## คำสั่ง

| คำสั่ง | ผล |
|---|---|
| `npm run data:build` | อ่าน `data/` แล้วสร้าง `lib/dataset.generated.json` ใหม่ |
| `npm run dev` | สร้างชุดข้อมูลแล้วเปิด dev server |
| `npm run build` | สร้างชุดข้อมูลแล้ว build |
| `npm test` | build แล้วรัน test ทั้งหมด (parser, engine, การจับคู่เอง/OTA, ฐานข้อมูล, UI) |

## การตั้งค่า

การตั้งค่าเป็นชั้นที่วางทับเอกสารต้นทาง ทำได้อย่างเดียวคือ **ไม่นำบางรายการเข้ากระทบยอด**
แล้วสั่งให้ engine คำนวณใหม่ทั้งรอบ ไฟล์ใน `data/` และข้อมูลในฐานข้อมูล**ไม่เคยถูกแก้ไข**
รายการที่ถูกตัดออกยังเรียกดูได้ครบที่หน้าค้นหา โดยเลือกสถานะ "ไม่นับ"

ค่าตั้งต้นของระบบตัดสองอย่างนี้ออก

| กฎ | ตัดอะไร |
|---|---|
| กลุ่มทรัพย์สิน `Medina` | ทุกรายการที่กลุ่มขึ้นต้นด้วย `Medina` เช่น `Medina-บางแสน` |
| ช่องทางรับเงิน `Kbank-Posh` | ทุกรายการที่รับเงินเข้าช่องทางนี้ |

รายการที่เข้าเงื่อนไข**ข้อใดข้อหนึ่ง**ก็ถูกตัดออก (เงื่อนไขแบบ *หรือ*)
กฎถูกตรวจตามลำดับ และรายงานเฉพาะกฎแรกที่เข้าข่าย

ตัวกรองอื่นที่เลือกได้: กลุ่มย่อยรายโครงการ · ช่องทางการจอง · สถานะคำจอง · คำค้น ·
ช่วงยอดเงิน · รายการคืนเงิน — ทุกตัวเลือกสร้างจากค่าที่มีอยู่จริงในเอกสาร พร้อมจำนวนรายการและยอดเงิน

ปรับได้อีกสองส่วน

- **การแตกยอด OTA** — ช่วงวัน (0–120 · ตั้งต้น 45 เพื่อให้คร่อมเดือนได้) · เพดานค่าคอมที่ถือว่าปกติ · ข้อความที่บอกว่าเป็นก้อนโอน OTA · ช่องทางที่ถือว่าเป็นเงินที่ OTA เก็บแทน
- **วิธีจับคู่** — เปิด/ปิด `N:1` และ `1:N` และจำนวนรายการสูงสุดต่อกลุ่ม (2–6)
  ส่วน **R01 วันที่** และ **R02 ยอดตรงพอดี** ล็อกไว้เสมอ แก้ไขไม่ได้

### ออนไลน์หรือเครื่องเดียว

| ตั้ง `DATABASE_URL` | ที่เก็บการตั้งค่าและการจับคู่เอง |
|---|---|
| ตั้งแล้ว | **Postgres** — ทุกเครื่องที่เปิดระบบเห็นค่าเดียวกัน ค่าเดิมถูกเก็บไว้ใน `audit_events` |
| ยังไม่ตั้ง | `localStorage` ของเบราว์เซอร์เครื่องนั้น ใช้งานได้ครบแต่เครื่องอื่นไม่เห็น |

หน้าจอบอกสถานะนี้ตลอดเวลาที่มุมซ้ายล่างและบนหน้าตั้งค่า ไม่ต้องเดา
โหมดเครื่องเดียวยังส่งออก/นำเข้าไฟล์ตั้งค่าเป็น JSON ได้ตามเดิม

## Deploy บน Vercel

เป็น Next.js มาตรฐาน Vercel ตรวจจับเองได้ ไม่ต้องตั้งค่าเพิ่ม หน้า `/` ถูก prerender เป็น static
ส่วน `/api/dataset` เป็น serverless function

เนื่องจาก `data/` ไม่ได้อยู่ใน repo การ deploy จาก GitHub จะได้ **ตัวระบบเปล่า** ซึ่งเป็นสิ่งที่ตั้งใจ —
ระบบขึ้นได้ ใช้งานได้ และรอโหลดเอกสารจริงทีหลัง

การโหลดข้อมูลเข้าระบบที่ deploy แล้ว: วางไฟล์ใน `data/` บนเครื่อง แล้ว

```bash
npm run data:build     # แปลงเอกสารเป็นชุดข้อมูล
npx vercel --prod      # deploy พร้อมข้อมูล (CLI อัปโหลดจากเครื่อง ไม่ผ่าน GitHub)
```

> **ถ้า deploy พร้อมข้อมูลจริง** URL ของ Vercel เปิดสาธารณะโดยค่าเริ่มต้น ต้องเปิด
> **Deployment Protection** (Settings → Deployment Protection → Vercel Authentication
> หรือ Password Protection) ก่อนเสมอ และอย่า commit `data/` ขึ้น repo ที่เป็น public

ตั้ง `NEXT_PUBLIC_SITE_URL` ได้ถ้าต้องการกำหนดโดเมนใน metadata เอง มิฉะนั้นระบบใช้
`VERCEL_PROJECT_PRODUCTION_URL` ที่ Vercel ใส่ให้อัตโนมัติ
